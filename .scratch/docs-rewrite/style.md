# 文档重写准则

目标：任何新加入的人（或 agent）读一遍就知道「是什么、什么时候发生、会怎样、该做什么」，不需要猜。

## 写法

- 先写结论或规则本身，再写原因（只在不显然时写）。
- 一句话只讲一件事。主语写清楚：谁（用户 / 应用 / 手机 / 某个模块）在什么时候做什么。
- 用具体名字代替抽象词。禁用或少用：归属、语义、投影、租约、编排、承载、落在、收敛、口径、维度、闭环、抓手、语境、兜底。必须用时先用一句话定义。
- 规则写成可检查的形式：「X 时显示 Y」「不要做 Z，因为……」。不写「应当合理」「按需」「酌情」这类无法判断对错的话。
- 能举例就举一个最短的例子（一个文件路径、一条命令、一句界面文案）。
- 枚举用列表或表格；流程用编号步骤。
- 同一条规则只写在一个地方，其他地方链接过去。发现重复：保留在最该在的文件，删掉其他处。
- 删掉：历史过程、已经不成立的规则、代码或配置里一眼能查到的清单、空话。
- 中文为主；代码标识、命令、路径用反引号。中英文之间不强制空格，但同一文件保持一致。

## AGENTS.md 专用

- 只写「不看就会做错、且做错代价高」的规则，以及去哪里找更多信息。
- 每条都是可执行指令（做什么 / 不做什么 / 用哪个命令）。命令要能直接复制运行。
- 不复述代码结构；结构由目录和文件名说明。
- 长度：根 AGENTS.md 控制在一屏左右；子目录 AGENTS.md 只写该目录特有的规则。

## 产品规格专用

- 每条行为写「触发条件 → 用户看到的结果 → 下一步可以做什么」。
- 写用户能观察到的行为，不写实现方式。
- 界面文案原样加引号。

## 不能改的东西

- 保留所有对外链接、Ardot 链接和被其他文档引用的标题锚点。改标题时，全仓 grep 旧锚点并同步修改。
- 不改变规则的实际含义。发现规则之间互相矛盾或明显不合理时，不要自己裁决，在报告里列出（文件、两条原文、建议）。
- `designs/design.md` 的 YAML front matter 由脚本读取，结构不动；改完运行 `node scripts/design_tokens/lint.mjs` 和 `node scripts/design_tokens/generate.mjs --check`。
