## 基线与问题定位

基线提交为 `95b734ced8c4b2ceafabfad08821279e32668c52`，工作区起始无未提交变更。Flutter 严格静态分析及 Rust workspace 默认主机测试基线通过；真实设备用例的 ignored 不计通过。

## 分轮整改

1. 拆分应用契约、展示格式化及音源所有者，按职责迁移旧 `services/`，保留 Riverpod、typed route 与不可变快照；提取按主题/设备失效且合并读取的查询模块。
2. 将运行时媒体、命令与平台适配从组装入口分开，消除能力包对公共导出入口的反向依赖；文件浏览/索引与任务日志改为独立库，删除 `part` 依赖。
3. 按真实协议与生命周期拆分 scrcpy 内部模块；停止先摘除/取消，再在锁外清理；原生媒体分离包容量、解码回退及图像转换，移除全局缺失安全文档抑制并补足 FFI 中文说明。
4. 加入实际依赖图门禁，核对中文手写注释及受控产物生成链，继续审查整合后的状态投递与失败清理。
5. 交叉审查后补齐音源停止失败的有界清理、查询连接失效与宿主停止重连栅栏；将远控输入状态和设计系统分为独立所有者及单向依赖库。
6. 收窄路由注册豁免；以失败回归补齐 GOP 包数上限与旧 ABI 空数据拒绝；将活动登记表收敛为短锁所有权接口，消除状态等待造成的跨设备阻塞。
7. 再次交叉核对后，以失败回归修复旧音源快照覆盖新清理失败、释放时遗漏迟到音源，以及旧快捷键回执释放新捕获按键的问题；文件桥接区分执行结束与消费句柄释放，回收已结束但无人消费的终态句柄。
8. 用阻塞状态与真实 ADB 上传夹具收敛最后窗口/整设备停止、画质重建交接与音频启动取消；增加本机关闭发送栅栏及官方 smart socket 同步关闭，保留远端清理未核验边界。

末轮真实主入口验收发现：hot restart 指令成功且无未捕获异常，但界面实际进入启动错误页。原因是 Dart isolate 丢失旧宿主对象后准备了新端口，而进程内 Runtime 仍持有原连接策略。修复后先读取原生完整登记，严格核对策略并恢复旧端点；恢复失败不创建替代服务器，后续绑定失败也不关闭原 Runtime 使用中的宿主。应用精准回归 9 项通过，受控真实 ADB 恢复、失效端点拒绝和关闭重试 3 项通过，独立只读复核通过。

完整门禁曾分别发现 FRB 生成漂移、迁移测试的格式差异，以及任务日志压缩测试在并发构建下超过默认 30 秒；中止轮次不计完整通过。日志用例单跑通过，strace 确认原夹具执行 1104 次 fsync。改为预置连续序号的合法历史，再通过四次真实删除覆盖追加、非空压缩、压缩后的删除恢复与清空标记恢复，并校验旧迁移输入未修改；生产阈值、flush 和测试超时均未放宽。

另一轮全量 Rust 回归暴露重连取消测试把整条命令的持久化完成放入网络取消的两秒窗口。确定性阻塞持久化的夹具证明：子 token 已取消、真实 socket 已 EOF、设备已离线，命令仍需等待持久化。仅修改测试，分别核验同一两秒时限内的传输取消与释放持久化栅栏后的最终 `cancelled`；定向两项和严格 Clippy 通过，生产实现未改变。

## 顶层 Rust 与独立绑定迁移（进行中）

用户进一步明确：应用不能包含 FRB、Rust 或相关生成物；能力包隐藏绑定且不实现业务；Rust 统一放在同名顶层目录，容易由 Dart 完成的能力保留在 Dart。原阶段的完整门禁与 APK 不代表本轮验收。

Rust 已迁入顶层 `rust/`。ADB、scrcpy 各自的普通 API 库与 FRB 入口分开，scrcpy 宿主组合两个普通 API 库并公开配套 Dart 能力；跨动态库的连接句柄拒绝混用。Linux 实际 Native Assets 默认加载及通用 SDK 定向测试通过。配置统一迁到顶层 `flutter_rust_bridge*.yaml`，生成工具从仓库根读取同一份配置；重新生成后的隔离 `dart tool/generate.dart --check` 通过，复制输入和格式化的四项工具回归通过。

生产偏好导出已由 Dart 读取设备事实并组装 v1 白名单，Rust 导出实现与路由删除；设备遗忘成功后持久清理设备画质和设置。分发接线两项回归通过，确认失败不会清掉偏好，成功后重开不复活孤儿偏好。另以真实 JVM 用例复现冷启动自动应用关闭偏好会抹掉停止标记；限制自动请求保留该标记后，四组所有权契约通过。

保存回执与缓存已由 `ApplicationSession` 注入 `ApplicationCommandDispatcher` 的生产组装路径，预览、缩略图缓存、文件租约与交付账本共用应用 gate；旧 Rust 不再打开或写入 `media-cache.json`、`deliveries.json`。64 项定向回归、对应静态分析及 Rust core 编译通过，覆盖在途预算、全占用拒绝、旧文件保护、私有 pull 发布与驱逐、交付准入和跨缓存所有者交接失败。这里验证了这些模块与分发接线，尚未完成本轮应用宿主运行。

通用 ADB 文件执行已抽出宽元数据、原始路径、受控助手、精确暂存 FD 和取消屏障；本机目录事实无需设备连接。Dart 原生公开接口无法完整提供非 UTF-8 名称、lstat 和纳秒时间，因此仅此事实查询保留原生实现；排序、递归、冲突、缓存与任务日志仍归 Dart。类型化错误经真实 FRB 回归验证保留 `not_found`，不从展示正文解析控制流。精确 FD 发布目前只核验 Linux/Android 实现，其他宿主明确返回 `atomic_save_unavailable`，不以长度和修改时间冒充同一文件。

进一步排查发现热重启丢失旧缓存写租约时，原生文件 worker 仍可能写入暂存路径。SDK 已加入按调用方稳定名称接管的文件 scope：先撤旧代准入，取消并等待本机 worker、流与 FD 回收，再交付新句柄；失败仍拒绝新准入且可重试，不断开共享设备 Client。应用文件执行器现在要求明确 scope，最终组装必须在打开新缓存前完成接管，不能使用无 scope 默认值绕过。

Dart 设备记录、身份业务所有者和连接准入所有者仍在等待完整生产切换。身份的 RSA 校验、兼容指纹及 CAS 原子发布由通用 SDK 提供，应用负责来源选择、代次、受影响连接、迁移与候选绑定。应用身份事务现在先保存仅含公开事实的提交意图，再发布密钥和设备绑定；密钥已发布但记录提交失败、元数据已提交但旧连接退休失败，都在重开时按原事务核验，不扫描或复活已停用的专属密钥。全局身份变化即使没有继承记录，也必须退休未绑定的全局尝试。身份 29 项、连接准入 8 项及文件执行器 8 项共 45 项定向回归通过，对应静态分析通过；这些模块尚未完成生产接线，不能据此宣称原 Runtime 的设备业务已经移除。

## 进程监督与文件变更复核

2026-10-24 再次沿职责排查命名。记录模块保持 `DeviceRecord`／`DeviceRecordStore`；动态分组查询原名 `DeviceDetails` 容易被误认为详情值对象，现改为 `DeviceDetailsReader`／`device_details_reader.dart`，协调器、测试入口和当前架构正文同步，无旧别名或转发。其余已检查对象未因机械统一后缀而改名。

保持唤醒的成功关闭现在可报告受监督主进程退出，失败保留原句柄供重试；`remoteRestoreVerified` 仍为 false。该路径只定时报告用户活动，没有修改永久超时，也没有请求上游 CleanUp；其他捕获的主进程退出不能证明其清理子进程结束或设置恢复。此处没有实现物理显示恢复租约。

## 连接准入与文件回收复核

2026-10-24 继续沿已确认的资源所有权问题整改。上一阶段所列的连接准入、桌面恢复顺序及预览回收问题在本阶段实现修复；其主机验证不代替 Android 或物理设备验收。当前命名仍为 `DeviceRecord`／`DeviceRecordStore`，没有为兼容旧名增加别名或转发文件。

新连接在身份核验和旧连接活动退休之后、业务交付之前通过 `PhysicalDisplayRecovery`；原比例窗口也经过同一阶段。当前 owner 在 gate 内发现，Dart 固定身份后才授权原流恢复，取得持久 DONE 后另发 ACK；失败不尝试后继 owner。`PhysicalDisplayCommand` 统一短命令的串行写入、有界读取、完整终态与精确流释放，避免发现回执早到时并发写入。恢复失败直接结束本次准备，不伪装成地址错误继续尝试候选。运行中连接已经断开时，只有精确原生事实确认 closed 且捕获排空，才允许原显示租约及恢复命令排空本机流；不发恢复或 ACK、不宣称远端恢复，留待下一条已核验连接处理。

`ApplicationHost` 的桌面与移动恢复统一认领、排空捕获、恢复显示、释放本机流，再断开旧连接；桌面还核对成功认领服务器的真实 `serverId`。任一步失败保留同一连接及服务器依赖，恢复服务器失败也不能提前清空待扫描范围。应用 Session 并行发起文件任务取消和精确执行器停止，使关闭失败及时报告；失败的连接退休仍由原所有者保留，不能以 Future 返回代替资源退出。

预览通过 `FileReadBatch` 固定实际连接，保留 reader、writer、未交付读租约和同路径队列，确认 worker 与暂存资源释放后才交付或解除预算。普通文件调用在原生创建前登记精确执行对象；取消关闭失败时保留原会话、在途 next 与片段，不再重复向公开流抛错或丢弃读取责任。传输任务独立保留 `cleanupPending`、原执行对象和缓存租约，取消、关闭、移除及重启均不能绕过；清理成功只恢复已知结果，提交未知仍为未知。冷重开只在相同技术 key 成功换发新 scope，且真实 attach 契约已排空旧操作和暂存描述符时解除清理标记，不据此自动重放。

最终交叉审查又发现传输重启等待缓存预算期间，移除可删除任务而迟到重启重新写入日志。整改将重启、移除、取消及预算释放纳入同一批次生命周期，首次等待前取得准入，原预算释放中不能复用。首次创建传输也在迟到预算返回后复查取消与关闭；准备阶段和首条持久提交之后分别保留明确的租约责任。设备取消待准备排空后重新选择任务，关闭把已登记但未启动的任务收束为取消，避免首条日志回执期间漏掉后续项目。释放失败保留原对象供重试，删除已落盘也不能丢失预算责任。最终新增的十二项门闩回归与此前九项清理回归共二十一项通过，涵盖正反次序、旧预算释放、迟到申请和关闭重试。
